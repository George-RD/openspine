## Context

This is the first complete vertical delegation proof, not a Gmail-specific autonomy model. The action descriptor, concrete `gmail.draft.v1` implementation descriptor, `ResolvedActionContext`, generic `ReviewedActionScope`, scoped standing-rule matcher, shared `gmail.create_draft` executor, owner-review object, and typed `DelegationEvidence` already exist. This change wires the kernel callers and closes the four runtime gaps without inventing another authority object (D-007, D-146).

Counterparty erasure is entered at kernel-root `src/counterparty_erasure.rs`. It first writes an authenticated terminal-erasure ledger through `OverlayOperations::record_terminal_erasure`, closes the generation-local scope in memory, then runs `Store::mark_learned_artifacts_erased`. `store/learned_artifacts.rs::ensure_schema` creates `erased_counterparties(counterparty_id PRIMARY KEY, erased_at)`. The local erasure transaction inserts that marker with learned-artifact invalidation, audit, and runtime revocation in one `BEGIN IMMEDIATE`; filesystem key deletion is after `COMMIT`. The marker, not a key tombstone or a digest, is the SQLite admission predicate. The authenticated terminal ledger is a separate durable non-SQLite recovery source and is written first, so this change MUST NOT claim that the ledger, SQLite marker, and filesystem cleanup form one cross-store transaction. If the post-ledger local step fails, startup reconciliation re-applies the marker transaction.
The erasure mechanism is wired and unconditionally invoked at startup; it is reachable via an imported continuity ledger, while local origination is absent. `main.rs:303` calls `validate_startup_and_reconcile_overlay_terminal_erasures`, which reaches `counterparty_erasure.rs:89-104` and `finish_local_erasure` -> `Store::mark_learned_artifacts_erased`; the loop runs for ids carried by the authenticated terminal ledger. The sole local `record_terminal_erasure` caller is the direct `counterparty_erasure.rs:59-65` `erase_counterparty` entrypoint, which remains `#[allow(dead_code)]` with the comment `owner command is a follow-up`; overlay restore can import and propagate ids without originating them. Resolution (a) applies to local owner origination only: specify the startup-reconciliation test through the real production caller, retain the imported-ledger path as reachable, and name a local owner erasure command as the remaining origination condition. Adding that owner surface would contradict this change's boundary and deserves its own review.
The normal `email.create_draft` path is `api/actions.rs::post_actions` -> the initial `gate()` decision -> `resolve_scoped_admission` -> `consult_scoped_rule`/`Store::consult_and_reserve_scoped_rule` -> the shared executor. The scoped path is reached through `post_actions`; it does not call the later literal `consult_standing_rule_gate` branch. That action-keyed branch is guarded by `!scoped_unresolvable` and is not a fallback for a constructible-but-unmatched or unresolvable scoped context.

The change deliberately does **not** add `GmailDraftScope`, `thread_match`, `evidence_summary` on `StandingRuleManifest`, Gmail-specific matching, a second manifest validation layer, or a new `DelegationEvidence` schema. It also does not absorb the pre-existing #135 fired-token reviewed-context call-site defect: `consume_fired_pending_for_context` has scope/compatibility predicates at `standing_rules_fired_token.rs:60-105`, but the only production caller is `api/actions.rs:537-546`, whose `None, None` arguments match only rows whose stored digests are NULL. Scoped rows therefore fail closed and are currently unconsumable. The live fired-token path is latent today because the action-keyed scheduler at `api/actions.rs:601-611` hardcodes both digests to `None`, the Allowlist is empty, and `email.create_draft` is `DarkWindowPolicy::Prohibited`; its reachability condition is the empty dark-window Allow allowlist, not counterparty-ledger origination. The direct counterparty-erasure owner ingress remains a dead wrapper at `counterparty_erasure.rs:59-65`, but startup reconciliation is wired and reachable for imported authenticated terminal-ledger rows through `main.rs:303-309` -> `counterparty_erasure.rs:89-104` -> `finish_local_erasure` -> `Store::mark_learned_artifacts_erased`. #130 records local owner origination as absent, does not add an owner surface, and keeps the fired-token and erasure conditions distinct. Plaintext briefcase residue, pending-row/SYSTEM_SCOPE payload retention, owner-review-row erasure lifecycle, and the cross-store ledger/SQLite crash window remain named residuals.

The current scoped admission rejects only `CounterpartyRef::Unresolved` (`scoped_admission.rs:207-217`). `Bound` means that an identity was resolved; it does not mean the identity is still eligible for action. Those are different predicates, and the current code conflates “we resolved an identity” with “we may still act for it.” #130 places the erased-marker check immediately beside the unresolved guard and gives both failure modes production-entering tests: the pre-existing unresolved case is recorded as `unresolved_counterparty_falls_back_via_action_api`, while the new erased case is `scoped_email_create_draft_erased_counterparty_falls_back_before_effect`. The digest machinery cannot answer the second predicate: a reviewed digest can remain byte-identical after the identity is erased.

The fired-token branch is intentionally separate in `api/actions.rs`: `fired_pending` prevents scoped resolution at `:502`, and the token is consumed at `:529-546`. `Store::consume_fired_pending_for_context` has the #135 reviewed-scope/compatibility predicates at `standing_rules_fired_token.rs:60-105`, but the only production caller is `api/actions.rs:537-546`, which calls the wrapper with `None, None`; `pipeline/standing_rule_timer.rs:378-389` is test code, not a production caller. SQLite `IS ?` with NULL is NULL-safe equality, not a wildcard: the production caller matches only pending rows whose stored digests are NULL. Scoped rows therefore fail closed and are currently unconsumable.

This is inert by configuration today, and more precisely inert at the minting end. The dark-window Allow allowlist is deliberately empty at `action_catalog_contracts.rs:54-60`; activation and startup sweeps reject `Allow`, and `email.create_draft` itself is `DarkWindowPolicy::Prohibited` at `action_catalog_data.rs:84`. No token can be minted through the shipped catalog. Independently, the sole production scheduler at `api/actions.rs:601-611` is the action-keyed path (commented “the rule carries no reviewed scope”) and hardcodes both reviewed-scope and compatibility digests to `None`; no non-test production path writes non-NULL reviewed-context digests into `standing_rule_pending_actions`. The reachability condition is explicit: the path becomes mintable only after a future catalog change adds an action to the Allow allowlist, and that change must repair the reviewed-context caller before any token is redeemed.

The reflection miner's typed contract is complete in `schemas/delegation_evidence.rs`, including unique `decision_event_id`, one owner principal, one request-shape digest, and a context-class digest. The live scheduled path instead groups `(artifact_id, action_id)`, counts rows, emits no reviewed scope, and constructs free-text provenance. This is the same structural hazard seen elsewhere on the roadmap: a correct lower-layer contract exists, but the kernel caller never reaches it. The request-shape digest intentionally differs from the payload-digest `request_digest` computed by `api/worker.rs:241`; those names are subsystem-local and must not be conflated.

The pending Gmail write table is durable and currently write-only from the runtime's perspective: `pending_draft_writes` is inserted before `gmail.create_draft`, left `pending` for `DeliveryUnknown`, and resolved only for a known outcome. No read occurs before a retry. The response currently exposes quota/rate/dark-window metadata, while the scoped audit note has rule/version and digests but no resolved target. `email.send` is counterparty-facing and policy-denied in current fixtures, but the catalog's non-delegable set contains only overlay export/restore.

The miner-to-owner bridge is part of this change, but it MUST extend the existing proposal chain rather than create a direct review path. `reflection_miner_runtime.rs::dispatch_reflection_proposal` remains the production caller: it submits the exact serialized `ReflectionProposal` through `artifact.propose`, and `dispatch_artifact_propose` continues to parse, run the replay and risk-judge evaluation gate, persist the `ProposedArtifact`, persist both verdict rows in `eval_verdicts`, and promote the row to `review_required`. Refactor that existing handler's evaluation/persistence core to return an internal proposal receipt (proposal identity, exact artifact digest, action-request identity, both verdict identities, and the bound `VerdictEpochs`); the shell-facing path retains its existing artifact-activation notification, while the miner path consumes the same receipt and suppresses only that duplicate notification. No second evaluator, parallel matcher, or direct standing-rule mutation is allowed.

Only after the shared `artifact.propose` core returns `Allow` and a receipt does the miner path construct `OwnerReviewRequest::try_new`. Before `persist_owner_review`, `reflection_miner_runtime::dispatch_reflection_proposal` MUST verify that the receipt and stored `ProposedArtifact` row contain the exact proposed-artifact identity/digest, `review_required` state, and both persisted verdict row identities; a missing verdict, non-`review_required` row, or receipt whose verdict/artifact digest is not the proposal's digest fails closed, so no owner-review row is created and no activation is possible. The review object carries an immutable evaluation binding referencing the exact proposed artifact and both verdict rows/epochs, alongside the typed repeated-approval evidence and reconstructed generic `ReviewedActionScope`; that binding is included in the review's content-addressed bytes and binding digest.
The new miner evaluation-binding field on `OwnerReviewRequest` MUST be an `Option` with `#[serde(default, skip_serializing_if = "Option::is_none")]`. Legacy pending reviews MUST deserialize it as `None` and omit it when reserialized, preserving the legacy review bytes and `calculate_binding_digest()`/`binding_is_valid()` result. Add a regression test that loads a legacy review fixture and asserts its binding digest is byte-identical before and after the schema change.

Approval has a second, approval-time binding check folded into the same `BEGIN IMMEDIATE` transaction as `commit_artifact_activation` (or implemented inside that commit), at `store/owner_review_approval.rs::verify_miner_evaluation_binding` (a new helper in this change), rather than as a preflight read that could race with proposal/verdict mutation or delegating all controls to the existing activation currency check:

| Failure condition | Approval-time enforcement |
| --- | --- |
| absent verdict | Load `eval_verdicts` for the bound artifact and require both bound verdict row identities to be present; an empty or incomplete set is refusal. |
| verdict bound to a different digest or artifact | Compare each stored verdict's artifact/proposal identity and digest with the immutable review binding; any mismatch is refusal. |
| proposal is not `review_required` | Load the stored `ProposedArtifact` row and require its exact kind/id/version, artifact digest, and `review_required` state before activation. |
| stale compatibility/evaluation epoch | After the presence/identity/state checks pass, call the existing `store/eval_verdict_currency.rs::reject_stale_eval_verdicts` / activation currency path; stale axes refuse before state mutation. |

Only a binding that passes all four checks may use the existing artifact-activation commit/currency path with a fresh task grant. A failed check leaves the review pending and records a typed refusal; it MUST NOT activate a standing rule. The scheduled test enters through `reflection_miner_tick`, asserts the persisted review contains the exact proposal/verdict binding, and uses named `miner_proposal_missing_verdict_refuses_without_review_or_activation`, `miner_proposal_mismatched_verdict_refuses_without_review_or_activation`, `miner_proposal_non_review_required_refuses_without_review_or_activation`, and `miner_proposal_stale_verdict_refuses_without_review_or_activation` dispatch controls to assert no `OwnerReviewRequest` creation and no activation, plus `miner_review_approval_rechecks_bound_verdict_rows_before_activation` approval-time mutation controls to assert no activation. A miner that only emits a candidate, creates a direct un-evaluated review, or drops verdict currency cannot satisfy the proof.

For a miner-originated evaluation-bound review, `Reject` may take the existing disposition path, but `Approve` and `Narrow` are not allowed to use the generic direct-manifest shortcut. `Narrow` must serialize the narrowed proposal and re-enter the same `artifact.propose` evaluation/promotion core, then persist a replacement `OwnerReviewRequest` only after fresh passing verdicts and a new evaluation binding are returned; if that evaluation is absent, denied, stale, or incompatible, the original review remains pending and no replacement is stored. Non-miner reviews retain their existing lifecycle path.

The miner calls the shared `artifact.propose` core with `notify_owner: false`. That core must persist and evaluate the proposal without sending its generic owner-facing activation notification; only after the receipt and binding checks pass does the miner persist the review and send the rendered owner-review surface. This prevents a failed binding from leaving a misleading activation CTA and prevents duplicate notifications for one miner proposal.

Only the `RepeatedApprovals` evidence class crosses this change's reusable-delegation boundary: it requires the typed constructor's minimum count, unique decision events, one owner, one context class, and equal request-shape digest before a standing-rule candidate is emitted. Corrections, stated preferences, and consolidation remain proposed outputs under their existing lifecycle; a single approval or any non-repeated class cannot mint reusable scoped authority merely because it has an owner approval.

The evaluation gate retains replay-before-judge ordering. Replay first establishes that the proposed bytes and owner-control history are admissible under the deterministic first-cut evaluator; only then does the structural risk judge run, with both passing verdicts persisted and bound to the same proposal digest and epoch set. Reversing the order would make a candidate's structural result precede the history gate and obscure which evidence boundary refused it, while providing no weaker bypass because activation still requires both verdicts.


## Goals / Non-Goals

**Goals:**

- Make erased-counterparty refusal an admission invariant for both normal scoped admission and fired-token consumption, with the authoritative read in the same SQLite `BEGIN IMMEDIATE` transaction as rule selection/reservation or token claim/reservation.
- Revoke all matching stored scoped standing rules by the generic reviewed counterparty dimension, not only miner-produced learned-artifact rows, and stale their pending exceptions in the same lifecycle transaction.
- Persist enough typed, kernel-derived approval metadata to construct `OwnerApprovalEvidence` and `DelegationEvidence::repeated_approvals` without trusting caller counts or payload text.
- Make context-class grouping, decision-event deduplication, request-shape equality, and evidence-derived provenance copy observable in named tests.
- Make a pending unknown Gmail write fence a retry before any new effect or standing-rule budget reservation.
- Emit a truthful scoped responsibility receipt containing rule identity, resolved target, and post-reservation budget headroom.
- Make `email.send` catalog-owned non-delegable data and preserve fail-closed dispatch and manifest rendering.
- Leave explicit residuals for data erasure, cross-store recovery, and the latent #135 caller defect.

**Non-Goals:**

- No `GmailDraftScope`, `thread_match`, `evidence_summary`, or connector-specific matching. `Target` remains the narrow same-thread dimension; widening to same-counterparty-any-thread needs a generic optional-dimension/narrowing decision.
- No new `DelegationEvidence` fields or relaxed request-digest equality. `request_digest` is the task-shape/request key, not a payload digest; body bytes, message IDs, timestamps, and decision event IDs MUST NOT enter it. Payload variation in fixtures remains valid.
- No restructuring of fired-token dispatch to resolve a scoped context, no repair of #135's `None, None` production caller, and no claim that fired tokens are now fully safe. After #130, a token path checks erasure but still has the separately recorded #135 scoped-token redemption defect.
- No new manifest validation arms duplicating catalog/judge checks, and no manifest field duplicating evidence summary. The catalog supplies non-delegability and the owner-review object owns evidence.
- No exactly-once Gmail delivery claim, provider idempotency key, automatic reconciliation, briefcase encryption, `SYSTEM_SCOPE` artifact rewrite, owner-review row lifecycle sweep, or terminal-ledger/SQLite atomicity redesign.

## Decisions

### 1. Use the SQLite erasure marker, with early checks and transactional enforcement

Add a store-level `is_counterparty_erased(counterparty_id)` predicate that reads only `erased_counterparties`. Do not inspect the filesystem tombstone, key-ring memory, digest, or external ledger from the admission matcher.

There are two cheap entry checks:

1. In `resolve_scoped_admission`, immediately after the existing `CounterpartyRef::Unresolved` guard, read the bound identity and return the existing ordinary-approval/unresolvable outcome when the marker is present.
2. In the `api/actions.rs` `fired_pending` branch immediately before the existing `consume_standing_rule_fired_pending` wrapper, read the same store predicate for the grant's bound counterparty. This covers the fired-token entry path even though it does not enter scoped resolution. It is a fast fail only.

The load-bearing checks are inside existing store transactions:

- `consult_and_reserve_scoped_rule` checks `erased_counterparties` after `BEGIN IMMEDIATE` and before selecting compatible rules, reserving quota/rate, or scheduling any timer. A marker hit returns ordinary approval with no reservation.
- The common fired-token consumption transaction checks the marker before reading/claiming the pending token or inserting its reservation. The action layer supplies the bound counterparty identity for the early check; the store helper applies the same predicate in the token transaction. This does not restructure dispatch or claim to repair #135's reviewed-context inputs.

This ordering gives a clear linearization: if the erase marker commits first, the admission transaction sees it and refuses; if admission's immediate transaction starts first, the erase waits and is ordered after the admitted effect. The early read alone is deliberately not evidence of the guarantee; a test MUST mutate/remove only the transactional recheck and fail.

**Rejected alternatives:**

- Checking only `resolve_scoped_admission`: fired-token redispatch bypasses it, and a marker could commit between the read and reservation.
- Checking only before the fired-token wrapper: the marker could commit before the wrapper's conditional claim, so it is still a TOCTOU.
- Reading a key tombstone or in-memory key-ring state: those are outside the SQLite admission transaction and are not the durable authority predicate.
- Resolving `ScopedAdmission` for fired tokens and routing them through `dispatch_scoped_effect`: it would absorb an independent #135 caller defect, change a large dispatch chain, and is unnecessary for the #130 erasure invariant. The current scoped-token wrapper is fail-closed and the shipped catalog cannot mint tokens.

### 2. Sweep owner-review and miner-produced rules through one generic scope representation

`mark_learned_artifacts_erased` currently revokes only active `standing_rules` rows whose `(artifact_id, version)` appears in the learned-artifact provenance match set (`learned_artifacts.rs:726-747`). That reaches miner-produced rules but not owner-review-created rows inserted by `owner_review_approval.rs::approve_owner_review_and_activate_rule`, which have no `learned_artifacts` row. Identical authority with different erasure behavior based on who proposed it is not defensible; the owner-approved rule is the more dangerous survivor because it carries reviewed scope and needs no further approval.

Extend the same erasure transaction to inspect stored `StandingRuleManifest.reviewed_scope.scope.dimensions` through the generic `ReviewedScopeDimension::Counterparty` / `ReviewedScopeValue::Counterparty(Ulid)` representation. Reuse the canonical scope value accessor and the existing standing-rule lifecycle transition/stale-exception helper; do not compare connector-specific fields or recalculate a second digest. Revoke matching active, paused, and needs-review rows (already revoked rows are no-ops), stale all pending exceptions for each affected rule, and append the normal durable lifecycle evidence in that transaction. The erasure marker remains the shared predicate for future admissions and activation-time hardening.
This is a generic reviewed-scope sweep, not a new Gmail matcher. A rule without a counterparty dimension is not selected by this sweep; it is governed by its own catalog and lifecycle rules. The owner-review/miner provenance split is closed for matching scoped rules, while learned-artifact invalidation remains responsible for derived artifact state.

**Rejected alternative:** continue sweeping only learned-artifact identities. It leaves owner-approved live authority behind and makes deletion behavior depend on proposal provenance rather than the reviewed scope.

### 3. Persist typed approval context and construct the existing evidence contract

Add optional, backward-compatible typed context metadata to the persisted approval audit event (with defaults for historical rows and inclusion in the audit hash pre-image):
The record is serialized inside the existing approval audit payload rather than a new evidence table and carries the exact generic reviewed-scope values plus compatibility digest needed to reconstruct the owner-reviewed context. Historical approval events decode as absent and are never mined; new context fields are part of the existing audit hash pre-image.

- `context_class_digest`: the kernel first derives `ReviewedActionScope::derive(&resolved_context)?` and records that scope's `context_class_digest()` (the evidence/grouping key, including the generic action/descriptor class); this is distinct from the resolved context's `reviewed_scope_digest()` used as the standing-rule scope key over required dimensions.
- `reviewed_scope_digest`: the narrower standing-rule scope key derived from required dimensions, persisted separately from the evidence grouping key.
- `request_digest`: the kernel-derived `ResolvedActionContext::task_shape_digest()`.

The owner-approval path records these only after the context is kernel-resolved; an unresolvable context keeps the existing per-instance approval behavior but contributes no reusable-pattern evidence. Target and payload digests remain separate: the target digest is recorded as a target reference, and the payload digest remains the protected payload reference. No raw body, recipient list, message ID, timestamp, or decision event ID is placed in `request_digest`.

`reflection_miner_support` projects these fields into the miner's read-only evidence entry along with the existing audit event ID, owner principal, target digest, and payload digest. The scheduled runtime groups candidates by `(action_id, context_class_digest)`, deduplicates `decision_event_id` with a `BTreeSet`, and calls `DelegationEvidence::repeated_approvals`. That constructor remains the authority for minimum count, unique decisions, one owner, and equal request-shape digest. The resulting evidence's `approval_count`, evidence-set digest, and context digest feed the proposal; provenance copy is derived from `DelegationEvidenceKind::RepeatedApprovals` and renders `2 matching owner approvals`, not a free-text scheduler assertion.

Dropping request-digest equality and grouping only by context class is rejected: two approvals can share an account/target class while representing different task shapes, so that relaxation would produce a weaker reusable responsibility. The proposed fixture deliberately varies payload digest while retaining equal request shape to prove the fields are not conflated.

### 4. Make the pending-write fence a pre-reservation read

Give `pending_draft_writes` a stable, protected-reference request fingerprint (action, thread target, target digest, and payload digest; no body plaintext) and expose a store query for a pending row with that fingerprint. The insertion before the provider write records it atomically with the existing pending row. Existing databases converge through the normal additive schema migration.

After kernel target/payload resolution and before scoped consultation/reservation or the shared executor, query the pending fence. A hit emits owner-actionable audit evidence and leaves the decision at ordinary approval; it MUST NOT run Gmail, reserve standing-rule budget, or automatically resend. Known success/failure continues to resolve the row; `DeliveryUnknown` leaves it pending. This is a retry fence, not an exactly-once claim, and a later operator/reconciler may resolve it after checking Gmail.

**Rejected alternatives:** count-only queries (not identity-specific), action-request-ID-only matching (scoped direct requests mint a new ID), and automatic resend (Gmail create-draft has no idempotency key).

### 5. Return a scoped responsibility receipt without confusing it with review lifecycle

Add an optional kernel response receipt populated only by a scoped effective Allow. It contains:

- admitting standing-rule id and version;
- canonical resolved target reference(s) from `ResolvedActionContext`;
- quota remaining and rate remaining after the reservation.

The effective-Allow audit carries the same rule identity, target refs, reviewed-scope/compatibility digests, and headroom provenance. The response/audit receipt says that the responsibility admitted the effect; it does not say Gmail created or delivered a draft until the executor returns its truthful `EffectOutcome`. Owner-review decision receipts remain lifecycle receipts and MUST NOT be changed to claim an external effect (D-011 and #129).

### 6. Make non-delegability catalog data

Add `email.send` to `ActionCatalog::with_non_delegable` and add an exact `non_delegable_count()` assertion beside the existing catalog cardinality guards. The set has three production readers that must be characterized together: `openspine-authority/src/worker_grant.rs:99-102` rejects an attenuated worker grant with `MintError::ActionNonDelegable`, `overlay_eval_gate/eval_input.rs:213-216` feeds the catalog-owned denial into the judge, and `api/overlay_export_restore.rs:64-68` reads the set inverted as a requirement for its own trusted non-egress path. The new `email.send` entry tightens worker-grant attenuation across the authority boundary even though current worker fixtures use `email.send_draft`; the inverted overlay reader must continue to accept only the two overlay ids. Rename `overlay_export_restore_are_non_delegable_with_no_egress` so it no longer describes the whole set, and add a named `email.send` catalog/judge test. Do not add an `email.send` special case to `StandingRuleManifest::validate`.

### 7. Capability-map sequencing is a release gate

Implementation tests and owner-path evidence land first. The change is archived only after the complete positive path, a fallback/control path, the owner-review origination bridge, and truthful Resume/Pause refusal passes. After archive, the map is regenerated to the deferred end state below; this change does not claim `wired_into_lyra`.

### 8. Origination and existing owner-review transition boundaries

The origination bridge creates a `Pending` `OwnerReviewRequest` through the existing surface persistence helper, then uses the normal owner-review command/callback route. That route branches on the review's immutable evaluation binding: for a miner-originated bound review, Approval delegates to the exact evaluated `ProposedArtifact` activation/currency commit and Narrow serializes the replacement through the same `artifact.propose` replay/risk-judge/promotion core before persisting it; neither may call `approve_owner_review_and_activate_rule` or `store/owner_review.rs:304-307`'s direct replacement shortcut. The existing raw-SQL Approval and direct Narrow edges remain unchanged only for non-miner reviews, and #130 records that inherited boundary rather than silently treating it as proof for the miner path. The new origination test enters through the owner-facing terminal/Telegram route and asserts that both miner-bound Approval and Narrow retain their evaluation binding; a separate follow-up may unify the non-miner transition convention.

The Resume and Pause defects are in scope because they make the owner-facing lifecycle contract untruthful. `resume_standing_rule_revalidated` currently returns `Ok(false)` for expiry, drift, invalid scope, unavailable, and supersession, while `owner_review_decision.rs::commit_lifecycle` treats only `Err` as refusal and still commits a successful/replayed review receipt. `store/standing_rules_lifecycle.rs::pause_standing_rule` has the same false-success shape: its `UPDATE ... WHERE status = 'active'` returns `Ok(false)` for paused, needs-review, and revoked rules, and its `standing_rule.paused` audit is emitted only when the update changes a row, so a refused Pause has no refusal/lifecycle record beyond the unconditional owner-review decision row. Change the lifecycle result to distinguish `Resumed`, `AlreadyActive` (the legitimate Resume replay), and `Refused` for Resume, and `Paused`, `AlreadyPaused` (the legitimate Pause replay), and `Refused` for Pause; map `Refused` to `LifecycleRefused` before `commit_owner_review_decision`, preserve the respective replay as an unchanged receipt, and record `owner_review.decision_refused` for refused Pause as well as Resume. Exercise both refusals through `handle_terminal_message` (`/review ... resume` and the owner Pause command) in `terminal_review_resume_refusal_is_truthful` and `terminal_review_pause_refusal_is_truthful`; the owner must see a refusal, the rule must remain unchanged, no successful lifecycle receipt may be committed, and the durable refusal event must be present.

### 9. Capability-map end state: defer generic wiring

This change chooses the deferred end state rather than claiming generic Lyra wiring. After archive and passing the map gate, `capabilities/capability-map.json` MUST have:

- capability `progressive-delegation`: `state: "proof_in_progress"`, `blocking_issues: []`, `runtime_changes` containing archived non-integer id `ship-recurring-gmail-draft-proof`, `lyra_artifacts: []`, and no capability-level `owner_path_tests` (the map only permits those on a `wired_into_lyra` capability);
- selected proof `recurring-gmail-draft`: `kind: "selected"`, `selected: true`, `state: "shipped"`, and non-empty `owner_path_tests` naming the positive recurring-draft owner path plus fallback/control tests, while its `current_limit` says the generic Lyra product loop is still not wired;
- the other proofs remain unchanged, so exactly one proof remains selected.

The map is updated only after archive, then `node scripts/capability-map.mjs --write` regenerates the roadmap. No hand edit is made inside the generated roadmap markers. A later product-surface change may move `progressive-delegation` to `wired_into_lyra` only after adding Lyra artifacts and capability-level positive/fallback owner-path evidence.

## Risks / Trade-offs

- **External-ledger window:** the authenticated terminal ledger is durable before the SQLite marker. A failure between those steps can temporarily leave the external ledger ahead of the local marker; startup reconciliation repairs it. #130's invariant begins at the committed SQLite marker and does not claim cross-store atomicity.
- **Residual private data:** briefcases are plaintext SQLite JSON and can retain the counterparty/task/thread content; pending rows retain protected refs and may point at `SYSTEM_SCOPE` artifacts; owner-review rows can retain reviewed counterparty scope. These are recorded residuals, not silently claimed erased, and need a separate data-lifecycle change.
- **Miner/owner provenance:** erasure now sweeps the live standing-rule scope independent of learned-artifact provenance, but learned-artifact invalidation and owner-review row lifecycle remain separate stores/flows. A later change must make those residual records converge without weakening audit history.
- **Latent #135 token path:** the production wrapper's NULL arguments make scoped fired rows unconsumable, while current catalog policy makes token minting impossible. #130's marker check covers the path if a future allowlist makes it reachable, but does not repair reviewed-context revalidation or claim the token path is fully safe.
- **Over-blocking pending retries:** the stable fingerprint may conservatively fence a retry until an operator resolves an uncertain write. That is intentional; a false second Gmail draft is worse than delayed automation.
- **Audit compatibility:** new context fields are optional for historical events and must participate in the hash pre-image so the ledger remains tamper-evident. Historical rows without them cannot be mined as repeated scoped approvals.
- **Cross-protocol sweep safety:** using the generic `Counterparty` dimension can revoke any protocol's rule bound to the erased identity, which is intentional; no connector branch is allowed in the sweep.
