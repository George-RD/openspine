## Why

OpenSpine has the pieces of the first reusable-delegation proof, but the owner-facing Gmail draft path is not yet a complete vertical contract. The counterparty-erasure mechanism is wired and unconditionally invoked at startup when an imported continuity ledger carries an id, while local origination is absent: the sole local `record_terminal_erasure` caller is the `#[allow(dead_code)]` `erase_counterparty` wrapper, and overlay restore can propagate imported ids without originating them. A local owner-erasure command remains the missing origination surface; the startup sweep is a real production door, not a `NONE` caller. Repeated-approval mining still counts raw audit rows instead of the typed evidence contract, delivery-unknown writes do not actually fence retries, and the response does not return a truthful responsibility receipt. The catalog also does not make `email.send` non-delegable, so the reusable-authority boundary is partly policy convention rather than catalog data.

This change affects OpenSpine core runtime, schemas, kernel persistence/audit, and the capability-map evidence for the Lyra Gmail proof. It affects runtime authority, private-data references, Gmail connector access, and owner-facing action responses; it does not add a new owner surface or a second connector.

## What Changes

- Add the durable SQLite `erased_counterparties` marker predicate at normal scoped admission and fired-token entry, with authoritative checks inside the existing `BEGIN IMMEDIATE` transactions that select/reserve a scoped rule or consume a fired token. When an imported terminal-ledger id is present, an erased counterparty falls back to ordinary owner approval and consumes no standing-rule budget; the remaining reachability condition for locally originating such an id is an owner-erasure command.
- Sweep every stored standing rule whose generic reviewed-scope counterparty dimension names an erased identity, including owner-review-created rules that have no `learned_artifacts` row. Reuse the generic reviewed-scope value representation rather than introducing a Gmail-specific or serialized-JSON matcher, and stale any pending exception that the revoked rule could otherwise fire. Exercise the sweep through the real startup caller with a seeded imported terminal-ledger id, and record local `record_terminal_erasure` origination as the residual.
- Record the kernel-resolved context metadata needed by the typed `DelegationEvidence::repeated_approvals` contract on each eligible `email.create_draft` owner-approval audit: derive `ReviewedActionScope::context_class_digest()` for the evidence/grouping key, keep the narrower `ResolvedActionContext::reviewed_scope_digest()` as the standing-rule binding, and record request-shape digest from `ResolvedActionContext::task_shape_digest()`, target digest, and payload digest. Keep decision event identity from the audit event and the owner principal from the authenticated grant.
- Replace the scheduled reflection miner's raw `(artifact_id, action_id)` row count with typed `OwnerApprovalEvidence` construction and `DelegationEvidence::repeated_approvals`. Deduplicate decision event IDs, group by context-class digest, require the contract's owner and request-digest equality, and derive provenance copy from the evidence kind. Remove the raw-count and `reviewed_scope = None` path.
- Read the durable pending Gmail-draft-write rows before admitting a retry. A pending row for the same stable write identity must return the request to ordinary owner review without another connector write; resolving the row removes the fence. Preserve the existing conservative `DeliveryUnknown` reservation behavior and do not claim exactly-once delivery.
- Emit a responsibility receipt for a scoped delegated effect that names the admitting rule id and version, the resolved target, and post-reservation quota/rate remaining. The receipt is separate from an owner-review lifecycle receipt and MUST describe the effect admission, not claim an external result that was not observed.
- Add `email.send` to the catalog-owned non-delegable set so the reusable-authority judge/manifest path renders the catalog denial instead of duplicating an action-specific block in a manifest. Add named catalog characterization coverage.
- Add named owner-path, fallback, transactional-race, evidence-integrity, grouping, retry-fence, and store-level erasure-sweep tests. Rewrite `scheduled_reflection_miner_tick_mines_repeated_approval` so it fails when decision-event deduplication or context-class grouping is removed; do not merely extend the old raw-row fixture.
- Complete the miner-to-owner bridge without bypassing #133: extend the existing `dispatch_reflection_proposal` -> `artifact.propose` chain, bind both exact-proposal verdicts/epochs into the persisted `Pending` `OwnerReviewRequest`, and before persisting the review require both verdict rows, exact proposal/artifact identity and digest, and `review_required` state; approval must repeat those presence/identity/digest/state checks against stored rows inside the same `BEGIN IMMEDIATE` transaction as artifact activation (or folded into that commit), before the stale-epoch currency path. Fail closed with no review creation or activation on absent/mismatched/non-`review_required` dispatch inputs; fail closed with no activation on approval-time binding mutation. Re-evaluate a narrowed replacement through the same chain before storing it. Exercise a…
- After archive, regenerate the capability map in the deferred `progressive-delegation` end state: keep the generic capability `proof_in_progress` with no Lyra artifact claim, while marking the selected `recurring-gmail-draft` proof `shipped` with its named positive and fallback/control owner-path tests. Do not claim `wired_into_lyra` until a later product-surface change adds Lyra artifacts and capability-level positive/fallback evidence; then regenerate the roadmap with the capability-map script.

- The change deliberately does **not** add `GmailDraftScope`, `thread_match`, `evidence_summary` on `StandingRuleManifest`, Gmail-specific matching, a second manifest validation layer, or a new `DelegationEvidence` schema. It also does not absorb the pre-existing #135 fired-token reviewed-context call-site defect: `consume_fired_pending_for_context` has scope/compatibility predicates at `standing_rules_fired_token.rs:60-105`, but the production action caller and the timer test fixture both go through `consume_standing_rule_fired_pending` (`api/actions.rs:537-546` and `pipeline/standing_rule_timer.rs:378-389`), whose `None` arguments match only rows whose stored digests are NULL. Scoped rows therefore fail closed and are currently unconsumable. The live fired-token path is latent today because the action-keyed scheduler at `api/actions.rs:601-611` hardcodes both digests to `None`, the Allowlist is empty, and `email.create_draft` is `DarkWindowPolicy::Prohibited`. The counterparty-erasure entrypoint has the same wiring shape: `counterparty_erasure.rs:59-65` is `#[allow(dead_code)]` with the comment `owner command is a follow-up`, and a non-test caller census finds none. #130 records both mechanisms as latent, adds their future admission guards, and does not add an owner surface. Plaintext briefcase residue, pending-row/SYSTEM_SCOPE payload retention, owner-review-row erasure lifecycle, and the cross-store ledger/SQLite crash window remain named residuals.

## Capabilities

### New Capabilities

None. This change completes and hardens existing protocol-neutral capabilities rather than introducing a new capability namespace.

### Modified Capabilities

- `responsibility-contract`: owner-approval evidence must carry the resolved generic context and request-shape identities, and effect receipts must remain distinct from review lifecycle receipts.
- `standing-rules`: erased-counterparty admission/revocation, transactional checks before reservation or fired-token consumption, pending-write retry fencing, and scoped responsibility receipts.
- `reflection-miner`: repeated approvals are built through the typed evidence contract with exact deduplication and context grouping.
- `gate-action-api`: `email.send` is catalog-owned non-delegable data and remains fail-closed at dispatch.
- `digest-bound-draft-approval`: delivery-unknown pending-write rows are consulted before a retry; no exactly-once claim is added.

## Dependencies

The proof depends on the archived implementations and canon for #127, #128, #129, and #133, plus the existing `DelegationEvidence` contract and #135 pending-exception lifecycle. No new external dependency is proposed.

## Out of Scope

- No widening from same-thread `Target` matching to a generic same-counterparty policy; that requires a generic optional-dimension/narrowing API and a new decision.
- No second live authority object, connector-specific scope schema, or changes to Gmail send permissions.
- No claim that terminal erasure is atomically one transaction across the authenticated external terminal ledger, SQLite, and filesystem key cleanup. The SQLite marker is the local admission predicate only after its commit; ledger-first recovery remains a separate existing boundary.
- No deletion or encryption migration for plaintext briefcases, pending draft rows, `SYSTEM_SCOPE` artifacts, or owner-review rows.
