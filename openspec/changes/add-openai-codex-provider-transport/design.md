# Design: OpenAI Codex OAuth provider transport and tier routing

## Wire contract (verified against pi's working implementation and the first-party client)

### Authorization

- Authorize: `https://auth.openai.com/oauth/authorize`
- Token: `https://auth.openai.com/oauth/token`
- Client id: `app_EMoamEEZ73f0CkXaXp7hrann` (public PKCE client, no secret)
- Scope: `openid profile email offline_access`
- Redirect: `http://localhost:1455/auth/callback` - registered exactly; host `localhost`, path `/auth/callback`, port 1455. The loopback listener binds `127.0.0.1:1455` (localhost resolves there); `CallbackServer` ignores the request path, so no listener change is needed. When port 1455 is taken the listener falls back to a random port; for Codex that redirect would be rejected upstream, so `begin_with_client_id` refuses any non-1455 port for `openai-codex` before producing a URL.
- Extra authorize params: `id_token_add_organizations=true`, `codex_cli_simplified_flow=true`, `originator=openspine`.
- Exchange and refresh are form-encoded POSTs (`authorization_code` / `refresh_token` grants) exactly as already implemented.

### Account identity

`chatgpt-account-id` is REQUIRED on inference. It is decoded from the ACCESS token JWT payload claim `https://api.openai.com/auth` -> `chatgpt_account_id` (pi decodes the access token and rejects a missing account id; its token type carries no id_token). Decoding is base64url without signature verification - the value is used as a routing header for requests authenticated by the same token, so verification adds nothing. Extraction happens in `exchange_code` and `refresh_token`; a missing claim fails the login closed, and the same condition on a background refresh disables the credential as a definitive failure (leaving it enabled would loop every generate through backend-401 + refresh). The id is stored as vault identity metadata (`provider.openai-codex.account_id`) and resolved at call time alongside the access token. The refresher persists refreshed identity whether or not the provider rotated the refresh token. A credential stored by an older build without the id is backfilled from the stored access token's claim at re-bind time.

### Inference transport

- `POST <base>/codex/responses`, default base `https://chatgpt.com/backend-api`. The path, `originator`, `OpenAI-Beta: responses=experimental`, user agent, and `Accept: text/event-stream` constants live in `codex_fingerprint.rs` and the transport consumes them from there.
- Headers: `Authorization: Bearer <access>`, `chatgpt-account-id: <id>`, plus the fingerprint constants above.
- Body: `{model, store:false, stream:true, instructions:<system>, input:[{type:"message", role, content:[{type:"input_text"|"output_text", text}]}], text:{verbosity:"low"}, include:["reasoning.encrypted_content"], tool_choice:"auto", parallel_tool_calls:true}`. User turns carry `input_text` content, assistant turns `output_text`. `stream:true` and `store:false` are mandatory on this endpoint. `max_tokens` has no wire equivalent here; the spend cap and grant budgets remain the cost bound.
- SSE parse is line-based (LF and CRLF frame identically; blank line ends an event; bare `data:` lines and `[DONE]` are framing noise). Text accumulates from `response.output_text.delta`; every terminal (`response.completed`/`done`/`incomplete`) supplies output items as a fallback when no deltas arrived. `response.failed` and `error` events map to `GatewayError::ProviderError` with synthetic status 502 (the Onyx in-band `error_msg` precedent); a terminal whose nested `response.status` reports `failed`/`cancelled` is rejected whatever frame it arrived in; an `incomplete` terminal with text returns the fragment (owner-visible under WYSIWYS), and with no usable text fails naming `incomplete_details.reason`. A stream ending without a terminal event fails closed.
- The exact access-token and account-id strings are scrubbed to `<redacted>` from every error the transport returns, so a backend body or event echoing them never reaches kernel logs. Setup's probe redaction also covers the account id.
- 401 handling reuses the existing `generate_with_secret_store` refresh-once path; the retry re-reads the vault identity next to the refreshed token.

## Decisions

1. **New `ProviderKind::OpenaiCodex`, not a flag on `OpenaiCompat`.** The transport differs in URL shape, headers, body, and response format; the ambiguous state (Codex credential on a chat-completions client) is exactly what D-145 refused to store. A distinct kind makes it unrepresentable.
2. **Transport lives in `model_gateway/codex.rs`.** `providers.rs` sits at the 500-line cap; the SSE parser is independently testable. The Onyx transport moved to `model_gateway/onyx.rs` for the same gate.
3. **Dedicated Codex fingerprint module.** `provider_config_digest` binds an OAuth client fingerprint so a swap approval covers the real wire surface. Reusing the Anthropic fingerprint for Codex would bind constants Codex never transmits. `codex_fingerprint.rs` covers the identifying client surface the transport consumes - originator, beta, user agent, endpoint path, accept header - and `provider_config_digest` selects the fingerprint by kind. The request body shape is structural (booleans and typed items the endpoint mandates), pinned by the transport wire tests rather than a digest string.
4. **Tier resolution returns the provider id and client as one pair.** The id keys vault credential resolution (token, account identity, refresh). Handing callers the client alone invited pairing it with the active provider's id, which would spend one provider's vault credential against another provider's endpoint - with two subscription logins stored, a cross-vendor credential leak. `GatewayTierMap::resolve` and `WorkflowStateMachine::provider_for_step` both return the pair; `api/generate.rs` threads the routed id into `counted_model_generate`.
5. **Account id resolved at call time from the vault, passed to the transport.** The client is built at startup from config; tokens and identity live in the vault and may change on re-login. A Codex call with no stored account id fails with a `GatewayError` naming the re-login fix rather than sending a request the backend will reject opaquely.
6. **Dead device-code surface removed.** The endpoints (`/oauth/device/code`) never matched the real bespoke device-auth API (`/api/accounts/deviceauth/*`). The functions, `DeviceCodeResponse`, and the never-read `OAuthProviderSpec::{id, device_endpoint}` fields are gone, along with the stale `#[allow(dead_code)]` escape hatches. Headless logins paste the full redirected URL instead - `finish` parses `code`/`state` from a pasted URL or query string, keeping the existing `code#state` form. A pasted state must equal the flow's own (state round-trips verbatim in OAuth); presence alone triggers the check, so `state=` cannot bypass it.
7. **Switching = re-bind from stored credential.** `login_flow` short-circuits authorization when the vault already holds a non-disabled credential with a refresh token for the named provider: verify through the gateway, then re-bind roles in `openspine.yaml`. `--force` re-runs the authorization (e.g. to bind a different provider-side account). The shortcut sits BEHIND the spendability refusal (`client_id_for`), so a stored Antigravity credential stays refused. Binding is also a canonical-transport cutover: a legacy `openai-codex`/`openai_compat` entry gets the canonical kind AND its base_url reset, in both `provider_entry` (what verification runs against) and `update_openspine_yaml_roles` (what gets written) - the new transport's bearer and account header must never reach an endpoint configured for a different wire contract.
8. **`model_tiers` is owner-authored config, not a governed artifact.** The owner editing `openspine.yaml` is already the root of trust for the provider list and default provider; tier routes are the same class. Runtime swaps of the ACTIVE provider remain behind the AD-152 model-swap ceremony, which this change does not touch. Validation is fail-closed at startup: a tier route naming an unknown provider id aborts boot with the offending name. Honesty note: production `model.generate` declares `standard` today, so `standard` routes are live immediately; `low`/`high` reach real calls when kernel workflow-step driving lands (`WorkflowStateMachine::provider_for_step` is ready and returns the id+client pair; production driving stays deferred with D-090).

## Risks

- `originator=openspine` is an unregistered client name. pi ships `originator=pi` against the same endpoints successfully, so arbitrary originators are accepted today. If OpenAI ever allowlists originators, the constant is one greppable change (and bumps the fingerprint version by design).
- The Codex backend evolves without notice. The transport asserts only the minimal stable event set (`output_text.delta`, terminal `response.*` events, nested status) and surfaces unknown failures verbatim (scrubbed) in `GatewayError::ProviderError` bodies.
